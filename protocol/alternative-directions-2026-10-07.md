# Alternative research directions and selection

7 October 2026. Focused primary-source scoping, not exhaustive novelty clearance. Rankings below are research judgments based on contribution clarity, data fit and evaluation feasibility, not numerical novelty scores. The existing synthetic pilots and sealed 96-case validation specification remain unchanged and are not evidence for a new application domain.

## Recommendation

Prioritize a feasibility audit of **decision-relevant verification under shared advisory provenance**. Use reproducible software artifacts and public advisory snapshots to measure whether a second evidence source changes a remediation decision, distinguishing a genuinely new observation from another tool repeating the same upstream advisory. Retain the current exact model as an analytical reference. Do not commit to a final paper claim until independent labels and usable provenance are demonstrated.

The fallback is a bounded robustness study of the existing model. Moving directly to a new industry or adding a learned model is less defensible while measurement validity is unresolved.

## Source evidence and access limits

1. [A Ground-Truth-Based Evaluation of Vulnerability Detection Across Multiple Ecosystems](https://arxiv.org/html/2604.21111v1), 2026 preprint. Abstract, tool/advisory-source tables and discussion inspected. It compares detection using an OSV-derived reference across ecosystems. This establishes close overlap for scanner and ecosystem comparisons. The reference is advisory-derived; it should not be silently relabeled as observed exploitability or operational patch benefit. Its reported tool rankings are not independently reproduced here.

2. [A Reality Check on SBOM-based Vulnerability Management](https://arxiv.org/html/2511.20313v1), 2025 preprint. Abstract and framework overview inspected. It advocates accurate SBOM generation followed by function-call analysis to reduce noisy vulnerability reports. Combining SBOMs with reachability is therefore already covered at a broad level. Detailed evaluation and artifact reproduction remain pending before any direct comparative claim.

3. [OpenVEX specification](https://github.com/openvex/spec/blob/main/OPENVEX-SPEC.md), current documentation inspected. Statements already associate vulnerability, product, status and time; not-affected assertions have justification requirements. These semantics are existing baselines, not our contribution. A selective revalidation experiment would need to show behavior beyond ordinary identity and version handling.

4. [A robust statistical framework for cyber-vulnerability prioritisation under partial information in threat intelligence](https://arxiv.org/abs/2302.08348), 2023 preprint record. Abstract-level access identifies mid-quantile regression for ordinal assessments. It is a methodological overlap lead, not evidence that our proposed minimax policy is already implemented or absent. Read methods before proposing a robust-method novelty claim.

5. [Microsoft CyberBattleSim](https://github.com/microsoft/CyberBattleSim) and its [baseline benchmark](https://github.com/microsoft/CyberBattleSim/blob/main/docs/benchmark.md). Official overview and benchmark descriptions inspected. This is an abstract simulated environment, not a production outcome dataset. Its documented benchmarks do not by themselves validate our proposed paid-verification action.

Supporting acquisition leads: [OSV documentation](https://google.github.io/osv.dev/) and [Grype database builder](https://github.com/anchore/grype-db). Documentation access is not dataset acquisition, a license audit or reconstruction of historical scanner state. No new data was downloaded for this comparison.

## Concrete feasibility audit for the preferred direction

Start with a small development set of public, redistributable package artifacts and pin every version, digest, scanner binary and advisory snapshot. Inspect licenses before mirroring. For each finding record the original upstream advisory, aliases and tool/database version. An alias match is not enough to prove that two measurements are independent or copied; ambiguous lineage remains unknown.

Use independently checkable installed-version/build facts as the initial endpoint. If claiming reachable vulnerable behavior later, add a separately adjudicated code-level or local testbed label. Never label a report false merely because another scanner omits it, and never call package presence proof of exploitability.

Define the second action explicitly: a second scanner may reuse the first scanner's upstream database, whereas inspecting an installed version or build configuration can answer a different question. Measure wall time and analyst effort separately; do not assign arbitrary costs and call them operational measurements.

Predefine required information before scaling: reproducible artifacts, independently checkable labels, traceable or explicitly unknown source lineage, and enough cases where verification could change an action. Publish feasibility failures. Only after those gates pass should we freeze a new prospective study and decide whether the result merits a benchmark, methodological or application contribution.

## Combination rules

Join datasets only when identities, time windows and label meanings are compatible. Preserve original provenance and missingness. Split by project/advisory family and time where relevant to avoid copied examples crossing evaluation boundaries. Keep synthetic stressors distinct from measured errors. Require ablations that isolate each added dataset or model, plus an equal-budget baseline. Do not select the final test population after observing favorable results.

The current recommendation is a scoped research choice, not evidence that every possible method, industry or dataset has been exhausted. None of the six directions has confirmed novelty yet.
